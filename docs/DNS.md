# DNS Handling

## Overview

Open NetRoute includes a DNS relay designed to prevent selected DNS requests from being sent directly through the normal Windows DNS path when those requests can be intercepted and handled by the application.

DNS traffic is handled separately from the main TCP proxying path.

The current implementation captures DNS traffic, forwards DNS queries through the configured SOCKS5 proxy using UDP ASSOCIATE, and injects the resulting DNS responses back toward the requesting application.

> DNS relay is implemented and functional, but complete leak-proof DNS protection is not guaranteed.

## DNS Traffic Flow

The intended DNS flow is:

```text
Application
    │
    │ UDP/53
    ▼
WinDivert
    │
    ▼
DNS Relay
    │
    ▼
SOCKS5 UDP ASSOCIATE
    │
    ▼
DNS Server
    │
    ▼
DNS Response
    │
    ▼
DNS Relay
    │
    ▼
WinDivert Injection
    │
    ▼
Application
```

The DNS query is therefore transported through the SOCKS5 proxy rather than being sent directly to the configured DNS server by the intercepted path.

## Implementation

The DNS relay uses the SOCKS5 UDP ASSOCIATE mechanism.

The main responsibilities are:

1. Capture DNS UDP traffic.
2. Identify the relevant flow/process when possible.
3. Parse and forward the DNS request through the SOCKS5 UDP channel.
4. Receive the DNS response.
5. Reconstruct the response packet as required.
6. Inject the response back toward the originating application.
7. Prevent the relay's own traffic from being repeatedly intercepted.

The implementation uses a dedicated UDP/DNS forwarding path rather than treating DNS as a normal TCP SOCKS5 CONNECT request.

## Process Scope

DNS interception has an important Windows-specific limitation.

Windows DNS traffic may be generated by the Windows DNS Client service (`dnscache`) rather than directly by the originating application.

As a result, DNS interception cannot always be treated as a perfectly isolated per-application feature.

In some situations, a DNS request may appear to originate from a system networking component rather than the application that caused the lookup.

This means that DNS routing behavior can differ from ordinary TCP process-based routing.

## Fail-Closed Behavior

The DNS relay is designed to avoid silently allowing an intercepted DNS request to continue directly when the proxy-based DNS path fails.

When the relay cannot successfully handle an intercepted request, the intended behavior is to avoid treating the direct DNS path as an equivalent successful proxy route.

The exact behavior can still depend on the Windows networking stack and the application making the request.

## Tested Behavior

The DNS implementation has been tested for the core relay path, including:

* capturing UDP port 53 traffic;
* identifying DNS-related traffic;
* forwarding DNS queries through the SOCKS5 UDP ASSOCIATE path;
* receiving DNS responses;
* reinjecting DNS responses toward the requesting client;
* successful client-side acceptance of the returned DNS response;
* avoiding an observed packet-processing loop in the tested scenarios.

These tests validate the core DNS relay mechanism.

They do not prove that every DNS-capable application or every Windows networking configuration is completely leak-free.

## DNS Leak Limitations

DNS leak protection is not absolute.

Some specialized DNS leak tests can still detect DNS-related exposure in certain configurations.

Possible causes include:

* applications bypassing the normal UDP/53 DNS path;
* encrypted DNS protocols;
* DNS requests generated by Windows system components;
* applications implementing their own resolver;
* networking traffic that cannot be reliably attributed to the originating application;
* protocol behavior outside the interception scope.

For this reason, Open NetRoute should currently be described as providing **DNS relay and improved DNS privacy**, not as providing guaranteed leak-proof DNS protection.

## DNS-over-HTTPS and DNS-over-TLS

Traditional DNS interception does not automatically intercept encrypted DNS protocols.

### DNS-over-HTTPS

DoH sends DNS queries over HTTPS, commonly using TCP or QUIC.

Because the DNS request is embedded inside encrypted application traffic, a simple UDP/53 interception mechanism cannot identify the DNS query itself.

An application using DoH may therefore continue to resolve DNS through its own encrypted resolver.

### DNS-over-TLS

DoT sends DNS traffic through an encrypted TLS connection.

Like DoH, it does not expose a normal UDP/53 DNS request that can be handled by the current DNS relay.

Applications using DoT may therefore bypass the DNS relay.

## WebRTC, STUN, QUIC, and Other UDP

DNS protection does not prevent other forms of network exposure.

For example:

* WebRTC may use STUN to discover public network addresses.
* QUIC uses UDP and can carry application traffic without using a traditional TCP connection.
* Applications may use custom UDP protocols.
* Applications may establish direct connections outside the traffic patterns handled by the current interception layer.

These protocols are separate from DNS and require their own handling if complete traffic privacy is a goal.

## Scope

The current DNS implementation should be understood as:

* **Implemented:** UDP/53 interception and SOCKS5-based DNS relay.
* **Implemented:** DNS response reinjection.
* **Tested:** Core request/response relay behavior.
* **Not guaranteed:** Complete DNS leak prevention in every application and configuration.
* **Not automatically covered:** DoH, DoT, arbitrary encrypted DNS mechanisms.
* **Not equivalent to:** A full-system VPN DNS isolation mechanism.

## Troubleshooting

If an application appears to bypass the DNS relay:

1. Check whether the application uses traditional UDP/53 DNS.
2. Check whether the application has its own DNS resolver.
3. Check for DoH or DoT configuration.
4. Check whether the request is being generated through the Windows DNS Client service.
5. Check whether the application is using QUIC or another UDP-based protocol.
6. Compare results using both ordinary DNS tests and specialized DNS leak-testing services.

Different applications can produce different results even when the system configuration is identical.

## Future Improvements

Potential future improvements include:

* broader DNS attribution;
* additional encrypted-DNS handling;
* improved IPv6 DNS coverage;
* stronger system-wide DNS isolation;
* more comprehensive leak testing across applications and Windows configurations.

Until those areas are addressed, DNS relay should be considered an implemented but still evolving component of Open NetRoute.
