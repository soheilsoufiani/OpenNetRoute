# CLAUDE.md

## Project Overview

This repository contains an open-source Windows desktop application that routes traffic from selected Windows applications through a user-configured SOCKS5 proxy.

The goal is to provide a lightweight, transparent, user-friendly alternative to applications such as Proxifier, focused initially on:

- Windows

- SOCKS5 proxies

- Per-application proxy rules

- TCP traffic

- Process-based traffic selection

- Simple GUI

- Open-source distribution

The application must NOT require users to configure proxy settings individually inside their applications.

The user should be able to:

1. Configure a SOCKS5 proxy.

2. Select Windows applications/processes.

3. Start the proxy routing engine.

4. Have traffic generated by selected applications routed through the SOCKS5 proxy.

5. Leave non-selected applications unaffected.

# Architecture Rules

Follow these rules strictly.

1. UI must not directly manipulate packets.

2. UI must not directly call WinDivert.

3. UI must not implement SOCKS5.

4. SOCKS5 code must not depend on WPF.

5. Core business logic must not depend on WPF.

6. WinDivert implementation must be isolated behind interfaces.

7. Process detection must be isolated behind interfaces.

8. Networking components must support CancellationToken.

9. Long-running operations must not block the UI thread.

10. All disposable resources must be disposed correctly.

Prefer dependency injection and interfaces where they improve testability.

Do not over-engineer the project with unnecessary abstractions.

DO NOT attempt to implement the entire application at once.

Before implementing a new subsystem:

1. Explain the design.

2. Identify risks.

3. Define interfaces.

4. Implement the smallest useful version.

5. Write tests.

6. Build the solution.

7. Run tests.

8. Fix errors.

9. Only then move to the next subsystem.

# Phase 1 — Configuration

Implement models for:

- SOCKS5 server address

- Port

- Username

- Password

- Proxy enabled/disabled

- Application rules

Example conceptual model:

```
ProxyConfiguration
    Host
    Port
    Username
    Password
    AuthenticationType
```

Rules should support:

```
ApplicationRule
    ExecutablePath
    ExecutableName
    Enabled
    ProxyMode
```

Do not store passwords in plaintext if a secure Windows credential mechanism is practical.

For the first prototype, clearly document the security implications of the chosen storage mechanism.

---

# Phase 2 — SOCKS5 Client

Implement a robust SOCKS5 client.

Required functionality:

- TCP CONNECT

- IPv4

- IPv6

- Domain names

- No authentication

- Username/password authentication

- Connection timeout

- Read/write timeout where appropriate

- Cancellation

- Clean disposal

Create unit tests for:

- Method negotiation

- No-auth negotiation

- Username/password negotiation

- Invalid credentials

- Domain destination

- IPv4 destination

- IPv6 destination

- Server rejection

- Connection timeout

- Cancellation

- Malformed server responses

Do not proceed until the SOCKS5 implementation is independently testable.

---

# Phase 3 — Process Discovery

Implement Windows process enumeration.

Required information:

- PID

- Process name

- Executable path

Handle:

- Access denied

- Processes terminating during enumeration

- Missing executable paths

- 32-bit/64-bit differences where relevant

The UI should eventually be able to display something similar to:

```
Chrome
chrome.exe
C:\Program Files\Google\Chrome\Application\chrome.exe
```

Do not yet redirect traffic.

---

# Phase 4 — WinDivert Integration

Integrate WinDivert behind a clean interface.

First implement:

- Open

- Close

- Receive

- Send

- Filtering

- Cancellation

- Error reporting

Do NOT immediately implement SOCKS5 routing.

First prove that packets can be safely captured and logged in a controlled test environment.

The application must never accidentally create an infinite capture/injection loop.

All injected packets must be distinguishable from intercepted packets when necessary.

---

# Phase 5 — Process-to-Connection Mapping

Implement the ability to determine which process owns a network connection.

The design must consider:

- PID

- Local IP

- Local port

- Remote IP

- Remote port

- TCP state

- IPv4

- IPv6

Use appropriate Windows APIs.

Do not assume that a packet alone always contains the process ID.

The system may need to correlate packet information with Windows connection tables.

Document race conditions.

Processes can create and close connections very quickly.

---

# Phase 6 — TCP Redirection Engine

Implement the smallest possible routing engine.

Initial goal:

```
selected process
        ↓
    TCP connection
        ↓
   SOCKS5 proxy
        ↓
    destination
```

Only implement TCP CONNECT initially.

Do not attempt UDP support yet.

Do not attempt transparent UDP tunneling yet.

Do not attempt DNS interception yet.

Keep the first implementation simple and observable.

---

# Phase 7 — Application Rules

Implement rules such as:

```
chrome.exe → Proxy
firefox.exe → Proxy
game.exe → Direct
```

Rules should support:

- Executable path

- Executable name

- Enabled/disabled

- Proxy/direct mode

Define clear precedence if multiple rules match.

Document the rule evaluation order.

---

# Phase 8 — DNS

DNS behavior must be explicitly designed.

The implementation must avoid unintentionally leaking DNS requests outside the proxy when the selected application's destination is supposed to use the proxy.

Analyze:

- Local DNS

- Remote DNS through SOCKS5 domain resolution

- IPv4

- IPv6

- Applications that perform their own DNS

- DNS over HTTPS

- DNS over TLS

Do not claim "DNS leak protection" unless it has actually been tested.

---

# Phase 9 — IPv6

Explicitly test IPv6.

Decide and document:

- Whether IPv6 is supported

- Whether IPv6 is proxied

- Whether IPv6 is disabled

- How rules apply to IPv6

Never silently assume IPv6 behaves like IPv4.

---

# Security Requirements

Security is important.

Never:

- Hardcode proxy credentials.

- Commit credentials.

- Log passwords.

- Log authentication secrets.

- Disable TLS certificate validation.

- Execute arbitrary commands from configuration.

- Trust executable paths without validation.

- Download or execute remote binaries automatically.

Validate all user input.

Treat configuration files as untrusted input.

---

# Administrator Privileges

Packet interception may require elevated privileges.

The application must clearly detect insufficient permissions.

Do not silently fail.

Show a useful error explaining that administrator privileges are required for packet interception.

Avoid requesting administrator privileges for functionality that does not require them.

---

# Error Handling

Errors must be understandable.

Bad:

```
Error 87
```

Better:

```
Unable to start packet interception.
WinDivert returned error 87.
Check that the application is running with administrator privileges.
```

For developer logs, preserve technical details.

For users, provide actionable messages.

---

# Performance

The application should be lightweight.

Avoid:

- Busy loops

- Excessive polling

- Blocking the UI thread

- Creating unnecessary threads

- Allocating excessively for every packet

- Excessive logging in production

Use async APIs where appropriate.

Use CancellationToken for shutdown.

Ensure all background workers terminate cleanly.

# Safe Testing

Never use production credentials in tests.

Create a local test environment whenever possible.

Tests must not:

- Modify unrelated firewall settings

- Permanently alter routing tables

- Disable Windows security features

- Break the user's network configuration

- Leave background processes running

Integration tests must clean up after themselves.
